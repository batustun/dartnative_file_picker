# 0.1.0 device validation results

Evidence for the mandatory release gate in `../manual-test-matrix.md`. Nothing in
this file may be filled in from reasoning: every row is either an observation
made on the named device or it stays `—`.

No serial numbers, UDIDs, MAC addresses or account identifiers. Device model and
OS version only.

**Status: 0.1.0 FROZEN. Implementation frozen, automated validation passed, physical-device validation passed. 72 PASS / 2 NOT RUN. Release candidate ready, pending owner publication authorization.**

iOS: 40 rows pass on a physical iPhone 15 Pro Max (iOS 26.6).
Android: 19 rows pass on a Pixel 6 emulator (API 34). A physical Galaxy S23 Ultra (Android 16 / API 36) then exposed **F9**, which invalidated the default read path and the emulator's pass of it, and the follow-up `dumpsys` instrumentation exposed **F10**. Both are fixed and re-verified on that same device: R1 to R11 pass, R12 is unreachable because no installed provider on the device reports a null size. Grant behaviour was measured with `dumpsys activity permissions` from a cleared-data baseline of zero grants, not inferred from the UI.

> **Test 1.1 — the package's highest-risk assumption — PASSES on hardware.**
> An iCloud Drive document picked with `persistAccess: true` was reopened by
> `openPersisted()` in a new process after a genuine force quit, and read back to
> the same byte count. This is the only possible proof that iOS security-scoped
> bookmarks work here, since `.withSecurityScope` is unavailable on iOS and
> compiling proves nothing about it.

Measurement method: the example app logs every observable value under the
`DNFP-TEST` prefix. While the debugger is attached these are read from `dn run`;
after a force quit they are read from the device syslog via `idevicesyslog`, which
was verified to carry them. `dn screenshot` does not work on a physical iPhone and
libimobiledevice's screenshot service is unavailable on iOS 26, so logs are the
measurement channel.

Cold-relaunch tests must use a **release (or profile) build**, never debug. A
debug build launched from the home screen with no tooling attached cannot start
the engine at all:

```
[ERROR:flutter/runtime/ptrace_check.cc(75)] Could not call ptrace(PT_TRACE_ME):
    Operation not permitted
Cannot create a FlutterEngine instance in debug mode without Flutter tooling or Xcode.
```

Observed on iPhone 15 Pro Max / iOS 26.6: a pitch-black screen and **zero**
`dartnative:` log lines, meaning the Dart isolate never ran. JIT needs `ptrace`,
which iOS refuses outside a debug session. This is engine behaviour and has
nothing to do with this package, but it invalidates any force-quit test performed
on a debug build, so the persistence rows below are executed with
`dn run --release`. That is also the truer test, since release is what ships.

`print` / `debugPrint` output still reaches the device syslog in release, so the
`DNFP-TEST` measurement channel survives the switch.

Known precision limit: byte counts are logged in KB to one decimal, so a read is
compared against the provider-reported exact `size` as well. A truncated read
would have to land within ~100 bytes of the full size to escape both checks.

### Incidental observations from the re-verification run

Not matrix rows, but worth keeping because they are evidence about code paths that
exist precisely for cases nobody can schedule.

- `DNFilePicker: ignoring a result for unknown token 1790952966463755`, five
  seconds after a pick had already been delivered. The proxy activity was
  recreated and its `finish()` override reported a second time for a token the
  bridge had already retired. Handled exactly as designed: logged and dropped,
  with no crash and no spurious cancellation delivered to Dart.
- Picking the same Drive document twice in one session produced **one** grant,
  not two: `registerSession` removes the URI before re-appending it, so the
  ledger cannot accumulate duplicates of a document the user keeps re-picking.
- A grant record's `persistedCreate` changes when the same document is picked
  again, because `takePersistableUriPermission` recreates the record. The count
  does not change, which is the property that matters for the 512 cap.
